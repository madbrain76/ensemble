## Required corrections

1. **Public auth invocation cannot run.** `auth_command.go:RunAuthCommand` (lines 25–29) rejects `auth login --print-url`; both entry points pass their arguments to it unchanged. Current chapter §16.2 and §16.9 explicitly require this invocation, including on the supplied GUI executable. Support the specified print-only/suppressed-browser path in the existing shared owner. The command test currently exercises bare `login`, so it does not cover this defect.

2. **Completed SSE items disappear when terminal output is empty.** `internal/engine/responses_stream.go:parseResponsesSSE` handles `response.output_item.added` but not `response.output_item.done`; at `response.completed` it reconstructs exclusively from terminal `response.output`. A completed function call/reasoning item followed by `output:[]` is therefore lost, or rejected when a streamed key was recorded. This directly contradicts §16.7's requirement to retain completed output items when the terminal envelope omits output. Retain completed items by output index, reconcile with terminal output, and still require successful terminal completion before committing or dispatching. Preserve incomplete/failed/EOF refusal behavior; do not turn previews into permission to execute tools.

3. **Reasoning/default and explanation policy are not selected-model policy.** `internal/common/auth.go:ResponsesCapabilities` recognizes only `gpt-ch19-course`; `NormalizeOpenAI` defaults only that model and forces `RequireToolExplanation=true` for **every** Responses surface. Meanwhile `internal/common/actor.go:LookupModel` recognizes the chapter's `gpt-6.1-sol`/`gpt-5.6-sol` identities for transport/media, and the public human recipe uses `gpt-6.1-sol` with explicit high effort/detailed summary. `renderResponses` gates those fields on the synthetic-only helper, so that public setting is silently omitted for the chapter's real model. §16.7 requires supported models to receive defaults, summaries to default on when supported, and explanation-before-tool gating to be enabled only for models that benefit. Put the needed capability/default/policy decisions in the existing model contract and preserve explicit supported choices, including `none`. Do not solve this by declaring all OpenAI models reasoning-capable or by treating summaries as ordinary assistant explanation.

4. **Responses rendering does not detect ambiguous tool identity.** `internal/engine/responses.go:renderResponses` collects outputs into a global `map[CallID]Part`, overwriting earlier results, and emits that selected result for every matching call. It has no duplicate-call/result check or consumption boundary. Ambiguous reused call IDs across dialogue can therefore be rendered as apparently valid pairs with the wrong result instead of refused. This violates §16.7's actual-call pairing and argument/result-integrity requirement. Reject ambiguous identity or pair within an unambiguous call/result unit; retain the existing honest unknown-outcome placeholder for a genuinely missing result. Do not fabricate successful execution. **Correction:** `responsesParts` already tracks `calls[item.CallID]` and rejects duplicate IDs within parsed output; the earlier contrary parser claim is withdrawn. This finding requests a renderer correction, not a duplicate-ID parser correction.
