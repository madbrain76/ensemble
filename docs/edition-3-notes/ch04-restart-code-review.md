## Public-behavior findings

All candidate paths below are relative to `solutions/edition-3/main`.

1. **Killed jobs retain completion metadata (high).** `internal/jobs/jobs.go:141–145` writes `ExitCode` without checking terminal status. `internal/tool/command.go:59–66,92–93` sets it during stop/late completion; `Kill` sets `killed` first and then logs a fresh snapshot (`internal/jobs/jobs.go:204–231`). Thus killing an ordinary live process produces a public `Job.Data()`/`JobReport.Job` and `job_killed` payload with `status:killed` **and** `exit_code`; a late registered handler can similarly mutate a killed snapshot. `internal/tool/dispatch.go:155–160` hides the code in formatted text only. Preserve terminal truth in the retained record and serialized events, not just presentation; after kill, late completion must not add successful-completion metadata. Verify both explicit kill and shutdown, including a late handler.

2. **Output-only changes do not release a blocked wait (medium).** `internal/jobs/jobs.go:278–320` safely captures the notification channel under the state lock, but readiness is only timer expiry, terminal state, or a supplied regex match. With no pattern, a write wakes the select and immediately sends it back to sleep. A running handler that writes new text while `wait_for_job` is blocked therefore waits out the full delay. Chapter 4 §4.4 explicitly requires new output to wake an already-blocked waiter. Add the missing output-readiness semantics without making a supplied pattern match old bytes or losing the lock/channel ordering. The original has the same deficiency; it is not the governing contract.

3. **One-shot consumption is silent (medium).** `internal/tool/dispatch.go:60–73` correctly consumes before lookup, validation, refusal, setters, and controls, and `control:199–210` correctly starts replacement settings from fresh defaults. But `custom` only forces an ordinary job header (`:145`); neither that header nor control/error results identify the consuming call and consumed delay/pattern/cap. The setter reply also omits the promised consumption notice. Implement §4.5's leading diagnostic for every consuming call, including failed calls and another setter, preserving explicit override behavior. Do not replace the existing correct one-shot ownership with target matching.

4. **`cwd` overrides execute but are not recorded or reported (medium).** `internal/tool/command.go:36–44` resolves the override correctly, but `internal/common/job.go:19–26` has no cwd field and `internal/tool/dispatch.go:155–166` cannot print it. Merely detecting the input key to force a generic header does not meet §4.7. Retain the optional override in serialized `tool.job.cwd` and show the effective nondefault directory in the report; default cwd must remain absent/empty in that serialized field.

5. **Search output still grows entirely in memory before reaching disk (medium).** `internal/tool/tool.go:288–349` accumulates the recursive search's complete output in `strings.Builder`; the legacy execute adapter writes it to the job only after return (`internal/tool/dispatch.go:119–124`). Large/many matching files therefore produce neither progressive output nor bounded output-memory use; observation caps cannot help. `list_directory` likewise builds its complete output (`tool.go:251–263`). Stream result production into the existing job writer while retaining inherited ordering/context semantics. The latest `read_file` and PTY paths already stream; this is not a claim that those paths buffer. The original also buffers these helpers, so copying it is not sufficient for the current disk-streaming requirement.

6. **Job-output setup errors bypass correlated tool results (high).** `internal/jobs/jobs.go:94–118` can fail creating/opening the sidecar before invoking the `tool_called` callback. `internal/tool/dispatch.go:126–129` then returns an infrastructure error without a `tool_returned`; `internal/agent/agent.go:259–264` aborts the tool loop. For example, an unusable configured DataDir causes an otherwise ordinary/refused tool call to disappear from the required called/returned pairing instead of returning a correlated error. Preserve Chapter 3's error/refusal pairing even when job admission/output setup fails, without launching effects that have no output owner. This also applies to remaining calls in that response when dispatch aborts.
