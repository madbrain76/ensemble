## Lessons to carry into the assigned exercise

Keep the gateway an edge router owning connections, authorization and delivery;
it owns no Agents and performs no model inference. A public client must actually
work from an outside Go module without importing private runtime packages.
Follow real message delivery through independently built programs, not only
library construction. The existing ownership rules still govern each executable.

Authentication and authorization are separate: a key proves the configured peer,
while groups and contactability decide whether it may deliver this message.
Derive provenance from authenticated gateway state, never a sender's assertion.
A trustworthy header still does not mechanically prove that a model will reject
conflicting instructions in message content. Narrow-only child grants need both
an allowed subset and a refused over-grant control.

At-least-once delivery is not exactly-once execution. Verify the actual receipt,
queued offline delivery and reconnect boundary, and distinguish orderly restart
from abrupt-stop durability. The chapter describes periodic persistence; do not
infer lossless crash recovery from a clean shutdown. Test restored settings and
policy effects rather than only JSON existence.

## Verified explanation corrections for later authorship

The official [Noise specification](https://noiseprotocol.org/noise.html#overview-of-handshake-state-machine)
says the ephemeral public key is sent in cleartext. Its
[KK pattern](https://noiseprotocol.org/noise.html#interactive-handshake-patterns-fundamental)
uses each party's private keys and the peer's public keys to derive shared
transport keys. Thus the original's encrypted-first-ephemeral explanation and
requirement to hold both static keys are misleading. Explain authenticated
session encryption with its actual threat assumptions, without absolute secrecy
claims. [Payload security properties](https://noiseprotocol.org/noise.html#payload-security-properties)
distinguish handshake and transport guarantees, including forward-secrecy
conditions. Checked October11 against specification revision34 (2018-07-11).
These are prose corrections, not authorization to invent a cryptographic scheme.
