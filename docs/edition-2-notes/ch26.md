## Sourced carryover lessons

- **Activity is distinct from lifecycle.** §§26.1,26.4 separate thinking,
  tool execution, waiting and idle from running/done/failed state. Existing
  Observer delivery should carry the facts already known by the actor and
  waiting tools. Detailed status should identify the current work and usage;
  it must not claim that waiting proves the whole agent is harmless. Activity
  is monitoring, not an historical audit trail or proof of security.
- **Persistent peers and owned children have different lifetimes.** §26.2
  introduces a persisted registry of named peers and create/restart/delete
  behavior. Preserve conversation data across restart and refuse deletion
  with active children. The student already has a real Ensemble composition
  root; extend its responsibilities when assigned rather than recreate the
  first edition's manual wiring. Actual constructor/runtime checks remain
  necessary; successful compilation alone does not prove correct wiring.
- **Management tools must preserve owner scope.** §26.3 resolves a target
  through the caller's children, returning the same unknown-target result
  for another tree and a nonexistent target. Parent routing is not a license
  to expose a global fleet to model-callable tools. Keep actual runtime
  parent interfaces; do not import closure/service-bag architecture merely
  because the historical implementation used it. Verify existing25 ownership
  and every new target-bearing operation rather than deliberately weaken it.
- **Observe actual progress and preserve steering.** §26.4 adds change waiting,
  cursor-based output, asynchronous messages, synchronous questions, durable
  submissions, detailed status, kill and interrupt. Waiting must wake for its
  claimed conditions while preserving actual results. Interrupt ends a turn
  and keeps the Agent alive; shutdown/kill have separate lifetimes. Reuse the
  existing job/actor machinery. Polling versus notification details are a
  design choice, not permission to add a general event framework.
- **A tree needs real browser/runtime evidence.** §§26.5–26.7 require initial
  tree state and ongoing changes for nested agents, named-agent creation and
  deletion, and retained bottom-up submit/idle-correction behavior. Display
  activity and lifecycle separately. A parsed initial tree frame alone does
  not establish the complete interactive console. Required public vocabulary
  must be clarified narrowly at assignment if the source remains inconsistent.
