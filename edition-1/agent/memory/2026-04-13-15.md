## 2026-04-13: Puffin Data Model — Three-Tier Architecture

### What Was Built
1. **cr/docs/puffin-data-model.md** (315 lines) — Generalized family knowledge base data model with three-tier architecture.

### Key Design Decisions

**Three-tier data model with graduation path:**
- **Tier 1 (Go Core)**: Person, Contact, Event, Task, Alarm, EscalationChain — real Go structs. Calendar, task list, contacts, alarms. Every struct has a `Notes` field as the Tier 3 escape hatch.
- **Tier 2 (Templates + Scripts)**: Homebrew-VTT pattern. JSON templates define shapes, Python scripts handle type-specific logic. Medications, preferences, relationships start here. Cheap to iterate, no recompilation.
- **Tier 3 (LLM Free-Text)**: Person notes, event notes, per-person episodic memory cascade. No schema, maximum flexibility.

**Graduation path**: Free-text → template+script → Go struct. Ideas prove utility before getting promoted. Delete what doesn't work. "We don't know what we need and won't get it right upfront."

**Generalized for whole family**: Not a mom-care model — a family knowledge base. Bill's kids have ADD, Bill forgets things, Mom has memory decline. Same data model, different voice personality and escalation behavior per person.

**VTT conditions example validates the pattern**: D&D 5e conditions started as free-text key/value pairs (Tier 3). LLM forgets to apply them. Graduating to a conditions template (Tier 2) would give LLM structure. At scale, automated scripts (Tier 1) would handle saving throws deterministically.

### Considered and Rejected
- Hardcoded Go structs for everything (previous draft) — too rigid, we don't know what we need
- Pure grab-bag Items with no Go structs — Calendar, contacts, tasks, alarms MUST be reliable Go code
- JSON Schema validation (heavyweight) — VTT's lightweight example-instance templates work better
