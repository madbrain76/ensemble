## 2026-04-14: Twilio Research + Puffin Voice Architecture

### Research Findings
- **ConversationRelay** = AI is one side of a 1:1 call. Twilio handles STT/TTS, app gets text in/out via WebSocket. STT arrives as complete utterances (not streaming). App can stream TTS tokens back for low latency. Messages: setup, prompt, interrupt, dtmf, error (inbound); text, play, sendDigits, end (outbound).
- **`<Transcription>` TwiML** = silent observer of any call. Per-call-leg transcription with track labels. Posts webhooks. Works with Conference for per-speaker attribution.
- **ConversationRelay does NOT compose with Conference** — it's `<Connect>` vs `<Dial><Conference>`, separate TwiML branches.

### Two Distinct Call Types Identified
1. **Call Type 1 (ConversationRelay)**: Puffin calls a person — reminders, alerts, check-ins, escalation. Puffin IS the conversant. Simple robocall.
2. **Call Type 2 (Conference + Transcription)**: Bill calls Mom with Puffin listening. Human-to-human, Puffin silently observes. "Hey Puffin" wake word in gateway for interaction. Audio injection via Conference API.

### Decision: Start with Call Type 1
- Simpler, more urgent (Mom's reminders, Bill's alerts)
- Bill will put Mom on speakerphone + use Discord for Puffin interaction until Call Type 2 is built
- Phone call becomes a notification channel alongside ntfy and Discord

### Key Architecture Decisions
- Gateway owns the Twilio integration (WebSocket server, TwiML endpoint, REST client)
- Notifier triggers calls via gateway REST API (POST /api/calls), not via agent tool
- Gateway streams Puffin's response tokens back to Twilio for low-latency TTS
- No raw audio handling anywhere — text only
- Cloudflare tunnel for public HTTPS (already exists)
