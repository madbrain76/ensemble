## Session: Memory Cascade Design (2026-04-11)

### What Was Built
1. **cr/docs/memory-tree-design.md**: Theoretical comparison of 3 schemes (binary merge tree, K-ary rolling bins, optimal greedy K=8). Includes simulation at scripts/memory_tree_sim.py.
2. **scripts/memory_optimal_sim.py**: Dynamic K simulation — solves for K given total memory S and per-bin budget T. Shows optimal is 3-4 bins for 100K-500K tokens.
3. **cr/docs/memory-cascade-design.md**: Full implementation spec (839 lines) for Gemini 3.0 Flash. The chosen scheme is a binary cascade with 2× compression at each level.

### Key Design Decisions
- **Binary cascade with 2× compression**: Each bucket holds ~L bytes (~32KB). When uncompressed window exceeds 2L, oldest L bytes compressed 2× into bucket-0. Cascade upward when any bucket exceeds L.
- **Session-based memory files**: `YYYY-MM-DD-N.md` (one file per handoff, not appending to daily logs). Cascade splits at file boundaries — no line-range parsing.
- **Bucket format**: `cascade/bucket-N.md` with `<!-- cascade: covers X through Y -->` header. Dated `## YYYY-MM-DD` sections inside for parseable boundaries.
- **Go harness + sub-agent**: Harness does file math, sub-agent does LLM summarization via CompressFunc interface. Fake compressor for testing.
- **Async trigger**: Cascade runs fire-and-forget at handoff, doesn't block.
- **GetMemoryDir()**: Never hardcode ~/.cr/ — works for all agents (DesignGen, Homebrew-VTT, etc.)
- **6 implementation phases**: Core cascade → propagation → loader → handoff integration → migration script → cleanup.

### The Design Journey (Bill's thinking)
- Started with fixed K=8 (Optimal Greedy from previous session)
- Explored dynamic K (solve for K given total S) — found 3-4 bins optimal
- Bill: "what about 2× compression cascading?" — each level compresses 2× relative to previous
- Key insight: 2× is gentle enough that signal survives multiple rounds of cascading compression
- The big tradeoff: cascading 2× is ~80-90% as good as one-shot N× compression (reading all raw), but each compression operation is O(L) not O(S)
- Bill confirmed: this is nearly optimal for the cost

### What Was Considered and Rejected
- Fixed K schemes (K=8, K=4): partial bin problem, compound compression loss
- Dynamic K with variable bins: elegant but expensive (full re-read of all raw)
- JSON state file for tracking: parse filenames instead, self-healing
- Synchronous cascade at handoff: async is better, doesn't block
